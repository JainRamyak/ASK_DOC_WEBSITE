## Problem
A session's ChromaDB collection is deleted by the hourly cleanup sweep once it is older than `SESSION_TTL_HOURS` (default 24). "Older than" is measured from the collection's creation time and never updated, so a session that a user keeps actively querying/uploading to past the TTL window is deleted out from under them exactly like an abandoned one. Whether that is the intended behavior, or whether the TTL should instead reset on activity (upload/query), is not stated anywhere in the code, config, docs, or prior product decisions.

## Current Behavior
- FACT (code, `backend/src/storage/chroma_store.py:32-36`): `get_or_create_collection` passes `metadata={"hnsw:space": "cosine", "created_at": time.time()}` on every call, including calls against an already-existing collection (every `add()` call — i.e. every upload to an existing session — goes through `get_or_create_collection`).
- FACT (empirically confirmed this session, chromadb 1.5.9, the version pinned in `backend/requirements.txt` and installed in `backend/venv/`): when `get_or_create_collection` is called a second time against an existing collection name with a different `metadata` payload, the metadata is **not** updated — the collection keeps whatever metadata it was created with. Verified by direct API call: created a collection with `created_at=100.0`, called `get_or_create_collection` again with `created_at=200.0`, and both the returned object and a fresh `get_collection` still reported `created_at=100.0`. So on 1.5.9, `created_at` is fixed at first creation and is never touched by any subsequent upload, query, or delete against that session — confirmed CREATION-anchored, not just inferred from a code read.
- FACT (code): `cleanup_expired(ttl_hours)` (`chroma_store.py:119-132`) computes `cutoff = now - ttl_hours*3600` and deletes every collection whose `created_at < cutoff`, once per hourly sweep (`api/main.py:_session_cleanup_loop`, every 3600s from process start).
- FACT (code, grep across `backend/src` and `backend/api`): no code path writes a "last activity" timestamp anywhere. `/query` and `/upload` (append case) never touch collection metadata.
- INFERRED, not directly observed (matches `03-runtime-and-behavior.md` §2, §7, §9: "expiry itself not observed" — no test aged a real collection past 24h and watched the sweep act on it): the deletion mechanics themselves (sweep loop, `list_collections`/`delete_collection` calls) were not exercised live this session either; only the metadata-freeze behavior above was directly verified against a live chromadb 1.5.9 instance.
- UNKNOWN (flagged in backlog as G09-adjacent): the production Docker image pins `chromadb==0.6.3` (`backend/requirements.prod.txt`), a different major line from the `1.5.9` tested above (`backend/requirements.txt`). Whether 0.6.3's `get_or_create_collection` has the same "metadata frozen at creation" behavior is UNVERIFIED — not tested this session (would need a separate venv/install, out of scope for a spec).
- FACT (code): no query-time or race protection between the sweep and an in-flight request exists. `query()` (`chroma_store.py:98-104`) calls `self.client.get_collection(...)`, which raises `chromadb.errors.NotFoundError` if the sweep deleted the collection between request start and this call; `/query` in `main.py:290-295` catches all exceptions from `pipeline.ask` generically and returns a 500 with the raw exception detail in `HTTPException(status_code=500, detail=str(e))` — there is no dedicated "session expired" (`no_session`) response path visible in `main.py` today, contrary to `06-gap-analysis.md` G23's description of a `no_session` reason the frontend is expected to react to. This is itself a gap worth flagging (see Unknowns U2) but is not this spec's job to fix.

## Expected Behavior
Resolved via DECISION REQUIRED (below), Option 3: **activity-anchored idle timeout with a hard cap from creation.**
- A session expires once `SESSION_TTL_HOURS` (existing setting, default 24) have passed since its most recent `/upload` or `/query` — an idle timeout, not a fixed lifetime.
- Independently, a session also expires once `SESSION_MAX_LIFETIME_HOURS` (new setting) have passed since creation, regardless of how recently it was used — an absolute cap.
- A session expires at whichever of the two fires first. A session with no activity at all still expires at `SESSION_TTL_HOURS` from creation (creation counts as the first "activity").

## Root Cause
Undecided semantics — `REQ-U01` notes the anchor was never specified anywhere (code, docs, or archive), so the simplest implementation (stamp once at creation, never revisit) was built. Not a regression; a missing requirement.

## Scope
- Adding a last-activity metadata field to each session's collection, written on every `/upload` (new session and append) and every `/query` against that session.
- Adding a new config setting, `SESSION_MAX_LIFETIME_HOURS`, read via `config.py` (per CLAUDE.md's config convention), for the absolute cap.
- Changing `cleanup_expired` to delete a collection when *either* `now - last_activity_at > SESSION_TTL_HOURS*3600` *or* `now - created_at > SESSION_MAX_LIFETIME_HOURS*3600`.
- Using `collection.modify(metadata=...)` to update the last-activity field on an existing collection (confirmed this session: `get_or_create_collection`'s `metadata=` argument is ignored once the collection exists — see Current Behavior — so `modify()` is the only mechanism that actually updates stored metadata on chromadb 1.5.9). `modify()` replaces the metadata dict wholesale (confirmed empirically — a `modify()` call omitting an existing key removes it), so the implementation must read the collection's current metadata and write back the full merged dict, never a partial one.
- Tests for the above (idle-timeout expiry, hard-cap expiry, "whichever fires first", and that neither path breaks G01/G02/G27's existing store contract).
- Documenting both settings' meaning in `backend/.env.example`.

## Out of Scope
- Implementing a `no_session` response path if it doesn't already exist (Current Behavior, U2) — a separate, pre-existing gap. Left as an Unknown here; not fixed as a drive-by.
- G23 (frontend reaction to session loss/recovery) — related, separate backlog entry with its own spec.
- Validating chromadb 0.6.3's `get_or_create_collection`/`modify()` metadata behavior (production pin) — flagged as Unknown U1; would need its own investigation, possibly folding into G09/D-C02.
- Cross-process / multi-worker correctness (out of scope per the existing single-process assumption already documented in `chroma_store.py`'s lock comment).
- Changing `SESSION_TTL_HOURS`'s existing default (24) — only its *meaning* changes (idle timeout instead of fixed lifetime), not its value.

## Requirements
1. **R1 – Last-activity tracking.** Every successful `/upload` (new session or append) and every `/query` against a session writes a last-activity timestamp for that session's collection, using `collection.modify(metadata=...)` with the full existing metadata merged in (never a partial overwrite that would drop `hnsw:space`, `created_at`, or any other existing key).
2. **R2 – Idle-timeout expiry.** `cleanup_expired` deletes a collection whose last-activity timestamp is older than `SESSION_TTL_HOURS*3600` seconds, using the same config setting that exists today (`config.settings.session_ttl_hours`) — its default (24) is unchanged; only its meaning changes from "hours since creation" to "hours since last use".
3. **R3 – Hard-cap expiry.** A new setting `SESSION_MAX_LIFETIME_HOURS`, read via `config.py` (no ad hoc `os.getenv`), with an env var of the same name. `cleanup_expired` also deletes a collection whose `created_at` is older than `SESSION_MAX_LIFETIME_HOURS*3600` seconds, independently of R2.
4. **R4 – Whichever fires first.** A collection is deleted in a sweep if it satisfies R2 *or* R3 (logical OR, not AND); a session can never outlive the hard cap even if constantly active, and can never outlive the idle timeout even if it hasn't reached the hard cap yet.
5. **R5 – Creation counts as first activity.** A collection with zero `/upload`/`/query` calls after its creating upload still has a last-activity value (set at creation, same instant as `created_at`) and expires under R2 at `SESSION_TTL_HOURS` from creation if never touched again — matching today's observable behavior for a session that's used once and abandoned.
6. **R6 – No response-shape change.** `/upload`, `/upload-url`, `/query` response bodies are unchanged; the last-activity write is a side effect of a successful request, not a new field returned to the client.
7. **R7 – Failed requests don't extend liveness.** A request that raises before its ingestion/query work completes (e.g. validation failure, `HTTPException`) does not update last-activity — only a request whose underlying store operation (`add`/`query`) actually ran updates it.
8. **R8 – G01/G02/G27 preserved.** The `_add_lock`-protected id-assignment and content-hash-dedup logic in `chroma_store.add()` is unchanged by this spec; the last-activity write is additive to that method (and to `query()`), not a replacement of any existing behavior.
9. **R9 – `.env.example` documents both settings.** `backend/.env.example` states, for both `SESSION_TTL_HOURS` and `SESSION_MAX_LIFETIME_HOURS`, what each measures from and that a session expires at whichever fires first.

## Acceptance Criteria
1. AC1 (R1, R5): create a session (first upload), record its collection's last-activity value; it equals `created_at`.
2. AC2 (R1): query a session at some later time; the collection's last-activity value moves forward to (approximately) that query's timestamp, while `created_at` on the same collection is unchanged.
3. AC3 (R1): append-upload to an existing session at some later time; last-activity moves forward the same way as AC2.
4. AC4 (R2): a session whose last-activity is older than `SESSION_TTL_HOURS*3600` but whose `created_at` is within `SESSION_MAX_LIFETIME_HOURS*3600` is deleted by `cleanup_expired` (idle-timeout path fires).
5. AC5 (R3): a session that has been queried recently (last-activity fresh) but whose `created_at` is older than `SESSION_MAX_LIFETIME_HOURS*3600` is still deleted by `cleanup_expired` (hard-cap path fires despite recent activity).
6. AC6 (R4): a session inside both windows (fresh activity, within the hard cap) is not deleted; a session outside both windows is deleted exactly once (no double-counting/error from satisfying both conditions simultaneously).
7. AC7 (R7): a request that fails validation before reaching the store (e.g. `/query` with an invalid `session_id`, `/upload` exceeding `max_files_per_upload`) does not change any existing session's last-activity value.
8. AC8 (R8): G01's concurrency regression test (`test_upload_concurrency.py`) and G27's dedup regression test (`test_upload_dedup.py`) pass unmodified after this change.
9. AC9 (R6): `/upload`, `/upload-url`, `/query` response JSON shapes are byte-for-byte the same (field set and types) as before this change, for the same inputs.
10. AC10 (R9): `backend/.env.example` has an entry for `SESSION_MAX_LIFETIME_HOURS` and an updated comment on `SESSION_TTL_HOURS`, both stating what each measures from.
11. AC11: the CI command (`pytest tests/test_embedder.py tests/test_web_loader.py -v`, from `backend/`) still exits 0; any new TTL test is keyless and either joins that CI set or is deliberately excluded like `test_pipeline.py`, and this exclusion is stated explicitly in the plan.

## Edge Cases
- Sweep runs exactly at a cutoff boundary (equality) — current code uses strict `<`; the plan should preserve strict `<` for both R2 and R3 comparisons for consistency, not introduce `<=` for one and not the other.
- Sweep deletes a session between an in-flight `/query`'s embedding step and its `collection.query()` call (race exists today regardless of anchor, per Current Behavior) — unaffected by this spec; still not fixed here (Out of Scope: `no_session` path, U2).
- `SESSION_MAX_LIFETIME_HOURS` set lower than `SESSION_TTL_HOURS`: the hard cap fires first for every session regardless of activity, effectively disabling the idle-timeout behavior — not an error case, just a config choice the operator can make; no validation is required to prevent it (R3/R4 don't require `MAX >= TTL`).
- A session queried/uploaded to at the exact instant `cleanup_expired` is mid-sweep for that same collection: the existing `_add_lock` covers `add()`'s own atomicity but not a race against `list_collections()`/`delete_collection()` in `cleanup_expired` — this is the same unresolved race noted above, pre-existing and out of scope to fully close here; the plan should note whether R1's `modify()` call needs to tolerate the collection having just been deleted (e.g. catching `NotFoundError` rather than crashing the request).
- Two back-to-back `/query` or `/upload` calls to the same session in rapid succession: each independently calls `modify()`; last-writer-wins on the last-activity value is acceptable (no requirement for these writes to be strictly ordered beyond wall-clock time).

## DECISION REQUIRED — Session TTL anchor: creation vs. last activity (2026-09-27, SPEC-G10-2026-09-27)

Question:
Should a session's `SESSION_TTL_HOURS` window be measured from when the session was **created** (current code, confirmed empirically this session), or from the session's **last activity** (most recent `/upload` or `/query`)? A third option (activity-anchored with a hard maximum lifetime) is included in case neither pure form fits.

Relevant evidence:
- Confirmed empirically (chromadb 1.5.9): `created_at` is stamped once at first collection creation and is never updated by any later call, including further uploads to the same session — the sweep's cutoff check (`chroma_store.py:cleanup_expired`) is unambiguously creation-anchored today.
- No product statement, requirement, or prior decision anywhere in the repo/docs states which anchor was intended (`REQ-U01`); this was flagged UNKNOWN at Discovery/Architecture time and carried through the backlog unresolved.
- Choosing activity-anchored requires a new write path (on `/upload` and `/query`) touching the same store code `add()`/`query()` already used by G01/G02/G27 — a real implementation cost, not just documentation.
- G23 (frontend session-loss UX) is more consequential if creation-anchored is kept (a user can lose a session mid-conversation with no warning); less consequential if activity-anchored is chosen (only truly abandoned sessions expire).

Available options:
1. **Creation-anchored (keep current code).** Every session has a hard lifetime cap of `SESSION_TTL_HOURS` from first upload, regardless of use. Simplest — zero code change, spec becomes documentation-only. Downside: an actively-used session can be deleted mid-conversation with no server-side signal distinguishing "abandoned" from "in use" (raises G23's stakes).
2. **Activity-anchored.** Session survives as long as it's used; expires `SESSION_TTL_HOURS` after the *last* `/upload` or `/query` against it. Matches typical "idle timeout" expectations. Needs: a last-activity write on two hot paths, a decision on where it's stored (new metadata key vs. repurposing `created_at`), and — because a long-lived active session no longer has a hard cap — no upper bound on storage retention for a session someone keeps polling forever (relevant to the "low-memory hosting" / "storage doesn't grow forever" comment already in `chroma_store.py:cleanup_expired`'s docstring).
3. **Activity-anchored with a hard cap.** Combines both: resets on activity, but never survives past some longer absolute maximum from creation. Handles both concerns above but is the most implementation work and introduces a second config value not currently in `config.py`.

Impact:
Option 1: no engineering cost; if wrong, users with long sessions lose their work/context with no warning (partially mitigated only if G23 ships a good recovery UX). Option 2: moderate engineering cost (two new write paths); removes the "surprise mid-conversation expiry" risk but reopens the storage-growth concern the TTL sweep exists to prevent. Option 3: highest engineering cost; most robust; needs a new config knob and its own default value decision.
Suggested (not decided): none — this is a product/UX call about how session lifetime should feel to a user, not something derivable from the code or its comments.

Status: RESOLVED (2026-09-27, owner via AskUserQuestion, session PhaseB_G10) — **Option 3: activity-anchored with a hard cap.** `SESSION_TTL_HOURS` becomes an idle timeout (measured from last `/upload`/`/query`); a new `SESSION_MAX_LIFETIME_HOURS` (default 168h/7 days, owner-confirmed) is an absolute cap from creation; a session expires at whichever fires first. Recorded in `docs/DECISIONS.md`. Requirements, Acceptance Criteria, Scope, Out of Scope, Edge Cases, Constraints, Unknowns and Assumptions above are written against this resolution.
