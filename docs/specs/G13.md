# G13

## Status
APPROVED (2026-09-27, SPEC-G13-2026-09-27)

## Problem
`/upload`, `/upload-url`, and `/query` return the raw Python exception text (`str(e)`) as the HTTP 500 `detail` for any unexpected server-side exception. The frontend (`humanizeError` / `parseErrorDetail` in `frontend/lib/api.ts`) passes that `detail` through to the UI unchanged, on the documented assumption that "the backend's own detail message... is meaningful as-is" — which is true for the deliberate 400s (e.g. `"Invalid session_id."`) but not for the unexpected-exception 500s, which were never written with an end user as the audience.

## Current Behavior
- FACT (code, `backend/api/main.py:192-196`, `/upload`):
  ```python
  except Exception as e:
      logger.exception("Upload ingestion failed")
      shutil.rmtree(tmp_dir, ignore_errors=True)
      _cleanup_if_new(session_id, is_new_session)
      raise HTTPException(status_code=500, detail=f"Ingestion failed: {e}")
  ```
- FACT (code, `backend/api/main.py:256-259`, `/upload-url`):
  ```python
  except Exception as e:
      logger.exception("URL ingestion failed")
      _cleanup_if_new(session_id, is_new_session)
      raise HTTPException(status_code=500, detail=f"Ingestion failed: {e}")
  ```
- FACT (code, `backend/api/main.py:299-301`, `/query`):
  ```python
  except Exception as e:
      logger.exception("Query failed")
      raise HTTPException(status_code=500, detail=str(e))
  ```
  All three already call `logger.exception(...)` before raising, so the full exception and traceback already reach the server log independent of this fix — only the client-visible `detail` needs to change.
- FACT (code, `backend/src/generation/answer_chain.py:76-79, 89, 92-94, 122, 125-127, 148, 151, 172, 175-177`): `answer()` (dispatched by LLM provider) raises `ValueError` for an unknown `LLM_PROVIDER`, `ImportError` when a provider SDK isn't installed, and `EnvironmentError` when the provider's API key env var isn't set. Example message: `"GEMINI_API_KEY is not set in .env. Get a free key at https://aistudio.google.com"`.
- FACT (code, `backend/src/pipeline.py:222`): `answer()` is called only from `AskMyDocsPipeline.ask`, which is called only by `/query` (`backend/api/main.py:296-298`). `/upload` and `/upload-url` never reach `answer_chain.py` — their 500s come only from ingestion failures (file parsing, disk I/O, ChromaDB errors), not from LLM/provider configuration.
- FACT (code, `frontend/lib/api.ts:35-42`):
  ```ts
  async function parseErrorDetail(res: Response): Promise<string> {
    try {
      const body = await res.json();
      return body.detail ?? `Request failed (HTTP ${res.status})`;
    } catch {
      return `Request failed (HTTP ${res.status})`;
    }
  }
  ```
  and `humanizeError` (`frontend/lib/api.ts:12-23`) returns `ApiError.message` (i.e. this `detail`) verbatim for any `ApiError`. There is no client-side filtering of `detail` content by status code today — whatever the backend sends as `detail` on a 500 is what the user sees.
- OBSERVED (`docs/project-assessment/03-runtime-behavior.md` §4, cited by `docs/project-assessment/06-gap-analysis.md` G13 and `docs/PROJECT_BACKLOG.md` G13): a query against a session with no LLM key configured produced a 500 whose body surfaced the exact `"GEMINI_API_KEY is not set..."` message to the (simulated) end user.
- FACT (`backend/api/main.py:325-327`, `/feedback`): already returns a fixed, safe message (`"Could not record feedback"`) on its only 500 path — out of scope, no change needed.
- FACT (`docs/project-assessment/05-requirements.md` REQ-E16 vs REQ-B10): REQ-E16 ("users get comprehensible error messages") and REQ-B10 (current `str(e)`-as-`detail` behavior) are recorded as conflicting; this spec resolves that conflict in REQ-E16's favor for the three routes above.

## Expected Behavior
- `/upload`, `/upload-url`, and `/query` never place raw exception text, tracebacks, file paths, library names/install instructions, or environment-variable names/values in an HTTP response `detail` sent to the client.
- The full exception (message + traceback, via the existing `logger.exception(...)` calls) continues to reach the server log unchanged — this fix touches only the client-visible `detail` string, not logging.
- Two client-visible categories, per the approved decision below:
  1. **Configuration error** (LLM provider misconfigured): `/query` only, when the underlying exception from `answer_chain.answer()` is `EnvironmentError`, `ImportError`, or the "unknown `LLM_PROVIDER`" `ValueError`. Maps to `HTTPException(status_code=503, detail="The assistant is temporarily unavailable. Please try again later.")`.
  2. **Generic unexpected error**: every other exception on `/upload`, `/upload-url`, and `/query` (including all `/upload`/`/upload-url` failures, which never reach `answer_chain.py`). Maps to `HTTPException(status_code=500, detail="Something went wrong while processing your request. Please try again.")` — one shared literal string used identically by all three routes' catch-all handlers (approved decision: single shared generic message, not per-route wording).
- `/health` is unaffected — this spec does not change `/health`, and does not attempt to surface configuration errors there (that is G14's scope, only *softly* related here per the backlog's noted dependency: operator-visible guidance for a missing key must still exist via server logs, which `logger.exception` already provides and this spec does not remove).
- `/feedback`'s existing safe 500 message is unchanged.
- Client behavior is unaffected by this spec except that the *content* of what it displays for a 500/503 from these three routes changes — `humanizeError`/`parseErrorDetail`/`ApiError` plumbing itself needs no code change, since it already displays `detail` as-is.

## Evidence
- `backend/api/main.py:192-196, 256-259, 299-301, 325-327` (current 500 sites).
- `backend/src/generation/answer_chain.py:76-79, 89, 92-94, 122, 125-127, 148, 151, 172, 175-177` (exception types/messages that must not reach the client).
- `backend/src/pipeline.py:222` (confirms `answer()` — and thus config errors — is reachable only via `/query`).
- `frontend/lib/api.ts:12-23, 35-42` (client displays `detail` verbatim; no change needed there).
- `docs/project-assessment/03-runtime-behavior.md` §4 (OBSERVED leak).
- `docs/project-assessment/06-gap-analysis.md` G13; `docs/project-assessment/05-requirements.md` REQ-E16, REQ-B10; `docs/PROJECT_BACKLOG.md` G13.
- Owner decision (this session, via `AskUserQuestion`, 2026-09-27): (1) configuration errors get a distinct 503 with a fixed message, separate from a generic 500 for all other unexpected errors; (2) the generic message is a single shared string across all three routes, not per-route wording. Recorded as a `DECISION` in `docs/DECISIONS.md` (to be added on spec approval).

## Reproduction
1. Unset/blank the configured LLM provider's API key env var (or set `LLM_PROVIDER` to an unsupported value) and start the backend.
2. Upload a document, then `POST /query` a question against it that clears the relevance threshold (so the pipeline reaches `answer_chain.answer()`).
3. **Current:** response body `detail` contains the raw message, e.g. `"GEMINI_API_KEY is not set in .env. Get a free key at https://aistudio.google.com"`, with status 500.
4. **Expected after fix:** status 503, `detail: "The assistant is temporarily unavailable. Please try again later."`; the raw message and traceback appear only in the server log (`logger.exception` output).
5. Separately, force an ingestion-path exception (e.g. induce a ChromaDB error, or any exception inside the `try` blocks in `/upload` / `/upload-url`) and confirm the response is 500 with the shared generic message, not `f"Ingestion failed: {e}"`.

## Root Cause
The three `except Exception as e:` blocks in `backend/api/main.py` were written with `str(e)` as a debugging convenience (visible immediately during manual/local testing) and never revisited before the frontend started rendering `detail` unfiltered to end users.

## Scope
- `backend/api/main.py`: the three `except Exception` blocks in `/upload`, `/upload-url`, `/query` (lines ~192-196, 256-259, 299-301).
- Distinguishing the configuration-error subset within `/query`'s catch-all (catching `EnvironmentError`/`ImportError`/the unknown-provider `ValueError` ahead of, or within, the generic `except Exception`, and mapping to 503 with the fixed message).
- No frontend code changes (per Expected Behavior above, `parseErrorDetail`/`humanizeError` already do the right thing with whatever `detail` string they're given).

## Out of Scope
- `/health` readiness reporting (G14 — separately gated, softly related here only via the "operator must still see it" note in the backlog, which server-side logging already satisfies).
- `/feedback`'s existing 500 (already safe, no change).
- The 400-status `HTTPException`s in these routes (e.g. `"Invalid session_id."`, `"url is required"`, file-validation messages) — these are deliberate, already user-appropriate, and REQ-E16 is not in conflict with them; not touched by this spec.
- Any change to log format, log level, or what `logger.exception` captures.
- Retrying, circuit-breaking, or any other resilience behavior for LLM provider failures — this spec only changes what the client is told, not how the backend responds to the failure otherwise.
- Adding new tests beyond what's needed to pin this spec's behavior (test authorship approach is G07's concern per `docs/PROJECT_BACKLOG.md`; this spec's Verification Strategy below describes what must be checked, not a test-suite redesign).

## Requirements
1. `/query`'s 500/503 mapping must distinguish, by exception type raised from within the `try` block, between configuration errors (`EnvironmentError`, `ImportError`, and the `ValueError` raised by `answer_chain.answer()` specifically for an unrecognized `LLM_PROVIDER`) and all other exceptions.
2. A configuration error on `/query` must produce `status_code=503` and `detail="The assistant is temporarily unavailable. Please try again later."` verbatim.
3. Any other exception on `/query` must produce `status_code=500` and `detail="Something went wrong while processing your request. Please try again."` verbatim (same literal string as requirement 4).
4. Any exception on `/upload`'s and `/upload-url`'s existing catch-all blocks must produce `status_code=500` and `detail="Something went wrong while processing your request. Please try again."` verbatim (same literal string as requirement 3) — replacing `f"Ingestion failed: {e}"`.
5. In all three routes, the existing `logger.exception(...)` call (and any other existing logging/cleanup in that block: `shutil.rmtree`, `_cleanup_if_new`) must remain unchanged — only the `HTTPException(...)` construction changes.
6. No response `detail` for a 500 or 503 from these three routes may, under any circumstance, contain: an exception's `str()` representation, a traceback, a file path, a package/library name, an environment variable name, or a URL copied from an exception message.
7. `/feedback` and the existing 400-status `HTTPException`s across all routes are unchanged (see Out of Scope).

## Acceptance Criteria
- [ ] AC1: With a missing/invalid LLM API key (or unsupported `LLM_PROVIDER`) and a query that reaches `answer_chain.answer()`, `/query` returns HTTP 503 with `detail` exactly `"The assistant is temporarily unavailable. Please try again later."`.
- [ ] AC2: With any other exception raised inside `/query`'s `try` block (e.g. a forced/mocked exception unrelated to LLM configuration), `/query` returns HTTP 500 with `detail` exactly `"Something went wrong while processing your request. Please try again."`.
- [ ] AC3: With an exception raised inside `/upload`'s `try` block, the response is HTTP 500 with `detail` exactly `"Something went wrong while processing your request. Please try again."` (not `f"Ingestion failed: {e}"`).
- [ ] AC4: With an exception raised inside `/upload-url`'s `try` block, the response is HTTP 500 with `detail` exactly `"Something went wrong while processing your request. Please try again."`.
- [ ] AC5: In every case in AC1–AC4, the server log (via the existing `logger.exception` calls) still contains the original exception message and traceback — logging is provably unaffected.
- [ ] AC6: The pre-existing 400-status responses (`"Invalid session_id."`, `"url is required"`, `"session_id and question are required"`, question-too-long, file-validation messages, "no readable text" messages) are unchanged in status code and `detail` text.
- [ ] AC7: `/feedback`'s existing 500 behavior (`"Could not record feedback"`) is unchanged.
- [ ] AC8: No frontend file is modified as part of this fix (confirms the "no frontend change needed" scope call was correct — if it turns out one is needed, that is a spec gap, not a silent addition during implementation).

## Edge Cases
- A `/query` exception that is a subclass of `EnvironmentError`/`ImportError` raised somewhere other than `answer_chain.py` (e.g. from an unrelated dependency) would currently also be classified as a "configuration error" by a type-based `except` — acceptable per this spec (Requirement 1 is type-based, not call-site-based), since the 503 message is generic enough not to mislead in that case either.
- `ValueError` is also used elsewhere in the codebase for reasons unrelated to `LLM_PROVIDER` (e.g. validation). Requirement 1 only asks for the *specific* unknown-provider `ValueError` from `answer_chain.answer()` (message prefix `"Unknown LLM_PROVIDER="`) to be treated as a configuration error — a plain `except ValueError` in `/query`'s handler would be too broad and must not be used; the implementation must check `answer_chain`'s exception message/type precisely enough to avoid misclassifying an unrelated `ValueError` as a 503. (Left to implementation-planning: whether this uses a message-prefix check, a dedicated exception subclass in `answer_chain.py`, or a narrower `except (EnvironmentError, ImportError)` plus a distinguishable custom exception for the provider case — any of these satisfy the requirement; the spec does not mandate the mechanism.)
- `/upload` and `/upload-url` never raise these configuration-error types today (Evidence: `pipeline.py:222` shows `answer()` is unreachable from ingestion) — so their catch-all blocks need only the single generic 500 mapping (Requirement 4), no type-based branching.

## Assumptions
- ASSUMPTION: "Please try again later." is acceptable UX copy for the 503 case even though, for a genuinely broken configuration, retrying will not help until an operator fixes the env var — accepted because REQ-I10/G14 (operator-facing readiness signaling) is the mechanism intended to prevent this state from reaching users in the first place; this spec's job is only to stop the *current* leak, not to make the underlying failure self-healing.
- ASSUMPTION: The exact wording of the two fixed messages (503 and 500) is final as approved by the owner in this session and does not need further design/copy review.
