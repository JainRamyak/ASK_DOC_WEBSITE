# G29

## Status
APPROVED (2026-09-30, owner approval in session PhaseB_G29, after SPECVERIFY-G29-2026-09-30). Decision resolved (Option 1).

## Problem
When the configured LLM provider answers with a rate-limit (429) or overload (503) error, `/query` turns it into the same generic `500 "Something went wrong while processing your request. Please try again."` it uses for genuine bugs. The user cannot tell "the provider is busy, wait a bit" from "the app is broken", and nothing retries, so a momentary blip fails the whole question. Free-tier Gemini (5 requests/min/model) makes this reachable in normal use.

## Current Behavior
- FACT (code, `backend/api/main.py` `query_document`): `pipeline.ask` is wrapped in `except LLMConfigError` → 503 `CONFIG_ERROR_MESSAGE`, then `except Exception` → 500 `GENERIC_ERROR_MESSAGE`. Provider SDK errors are not `LLMConfigError`, so they hit the generic 500. Raw text stays in `logger.exception` only (G13).
- FACT (code, `backend/src/generation/answer_chain.py`): the four `_answer_*` functions call the SDK once, with no try/except, no retry, no backoff. SDK errors propagate raw.
- FACT (code): `rewrite_query` (opt-in, `ENABLE_QUERY_REWRITING`) swallows any exception and falls back to the original question. So a 429 on the rewrite call is already harmless by itself, but it spends one of the provider's request slots.
- FACT (code, `frontend/lib/api.ts` `humanizeError` / `parseErrorDetail`, `page.tsx handleAsk`): the frontend shows the backend's `detail` string verbatim in an error banner (`setError`). It does not branch on status code. No automatic retry. The user's question is cleared from the input and stays in the thread as a user bubble with no answer.
- OBSERVED (`docs/implementation/G05-observations.md`, 2026-09-29, direct SDK calls, not through `/query`):
  - Mistral: 429 `{"type":"rate_limited","message":"Rate limit exceeded","code":"1300"}` on 8 of 8 calls, returned in 0.5–0.7 s.
  - Gemini `gemini-3.6-flash`: 503 UNAVAILABLE "high demand" on 6 of 6 calls in one run and again on the first call of a later run (2–12 s each); then 429 RESOURCE_EXHAUSTED, free-tier limit 5/min/model, "retry in ~42 s"; later a fully successful run. So 503 was transient over minutes-to-hours, not seconds.
- NOT OBSERVED: what `/query` actually returns for these (G05 called the pipeline directly). The mapping to a generic 500 is read from code only.
- UNKNOWN: exception classes and status attributes for OpenAI and Anthropic overload/rate-limit in the installed SDK versions. INFERRED from SDK conventions: `openai.RateLimitError` / `anthropic.RateLimitError` (429), `anthropic` overloaded (529), `*.APIStatusError.status_code`. Must be confirmed against the installed packages during planning, not assumed.

## Expected Behavior
A provider 429 on the answer call returns HTTP 429 with the fixed message `RATE_LIMIT_ERROR_MESSAGE` = "The assistant is receiving too many requests right now. Please wait a moment and try again." A provider 503 (or the provider's overload equivalent) returns HTTP 503 with the fixed message `BUSY_ERROR_MESSAGE` = "The assistant is busy right now. Please try again in a moment." No retry. No `Retry-After` header. Everything else about `/query` (config errors with their distinct 503 message, other exceptions, success, grounding) is unchanged. Note the two 503s are distinguishable only by message text; that is accepted.

## DECISION REQUIRED — UX for provider 429/503 (2026-09-30, SPEC-G29-2026-09-30)

**Question:** When the provider returns 429 or 503 on the answer call, what should `/query` do and what should the user see?

**Relevant evidence:**
- `GENERIC_ERROR_MESSAGE` says "Something went wrong… Please try again", which is safe (G13) but misleading for a busy provider.
- G13 fixed that raw exception text must never reach the client; any new message must be a fixed string.
- Observed 503 lasted across several runs (minutes to hours); observed 429 said "retry in ~42 s". A short in-request retry (1–3 s) would not have helped in either observed case; it helps only for brief blips.
- Synchronous handler runs in the threadpool (`run_in_threadpool`); a retry with sleep holds a worker thread and lengthens the HTTP request. The frontend has a client-side timeout (see `humanizeError` "request timed out").
- Provider call counts are quota: retries spend quota (on a 5/min free tier a retry can cause the next 429).

**Available options:**
1. **Distinct status + fixed message, no retry.** Map provider 429 → HTTP 429, provider 503/overload → HTTP 503, each with a fixed "busy, try again in a moment" message (no raw text). Small, deterministic, no extra quota use. Users retry by hand.
2. **Option 1 plus bounded retry on 503/overload only** (e.g. 2 retries, short backoff, total time capped), never on 429. Hides brief blips; costs extra latency and quota on a failing provider; needs new settings (attempts, delay) in `config.py`.
3. **Option 1 plus a `Retry-After` header/field** when the provider supplies a wait (Gemini gave ~42 s), frontend shows "try again in ~N s". Best UX for quota; needs parsing provider-specific retry hints (different per SDK) and a small frontend change.
4. **Leave as is** (generic 500). Close G29 as accepted.

**Impact:** changes the `/query` error contract (status codes and message text), possibly adds config settings and a frontend tweak. Does not touch grounding, retrieval, CORS or URL allowlists.

**Recommendation:** Option 1. It removes the misleading "something broke" signal with the least code, no new quota risk and no new settings. Retry (2) and retry hints (3) can be separate items once there is evidence that blips are common.

**Resolved:** Option 1 (Distinct status, no retry), by owner via AskUserQuestion in session PhaseB_G29 (2026-09-30). Full resolution in `docs/DECISIONS.md`. Exact message strings above are drafted by the spec author and are part of what the owner approves.

## Root Cause
CONFIRMED (code): `/query` has only two exception buckets (config vs everything else), and `answer_chain` neither classifies nor retries provider errors. The SDKs raise distinct, status-bearing exceptions, but nothing inspects them.

## Scope
- Classifying provider rate-limit/overload errors from the answer call in `answer_chain.py` (a provider-neutral exception or equivalent), and mapping it in `/query`.
- Message text and status codes for that case.

## Out of Scope
- Config errors (G13/G14), grounding (G03), citations (G04/G30).
- Other provider failures (401/403 bad key, 404 bad model, 400, timeouts, content-filter). They stay in the generic 500 unless the owner says otherwise. Classification of 401/403/404 as config errors is a separate item.
- Provider failover, queues, or caching.
- Mapping errors from `/upload`, `/upload-url` (embedding uses the local embedder by default; API embedder errors are not covered here).
- Changing `rewrite_query`'s swallow-and-fallback behavior.
- Retry/backoff and retry-after hints (Options 2 and 3 of the decision, not chosen). Reopen as new backlog items if evidence shows blips are common.
- Any frontend change (the UI already shows `detail` verbatim).
- Any live provider call.

## Requirements
1. A provider error whose HTTP status is 429 returns HTTP 429 + `RATE_LIMIT_ERROR_MESSAGE`; one whose status is 503 or 529 (Anthropic "overloaded") returns HTTP 503 + `BUSY_ERROR_MESSAGE`. No other status is classified. Neither may produce the generic 500 message. Both messages are module constants next to `GENERIC_ERROR_MESSAGE`.
2. The client must never receive raw exception text, provider names in error bodies, request ids or keys; messages are fixed strings (G13 preserved).
3. `logger.exception` (or equivalent) still records the raw error server-side.
4. Classification must cover all four providers (gemini, mistral, openai, anthropic). It reads an integer (`int`, not bool/str) HTTP status from the exception (`status_code`, else `code`), not the class name, so no provider SDK has to be imported to classify. The attribute names per SDK must be confirmed against the pinned versions during planning (not possible in this session: SDKs are not installed).
5. Unclassified errors keep the existing generic 500; `LLMConfigError` keeps the existing 503 config message.
6. Success responses and the `grounded` / `sources` contract are unchanged.
7. No retry or backoff is added, no new settings, no `Retry-After` header, and no `frontend/` change.

## Acceptance Criteria
1. With a mocked provider error carrying status 429, `POST /query` returns HTTP 429 with `detail == RATE_LIMIT_ERROR_MESSAGE`, and the body contains no text from the exception.
2. With a mocked provider error carrying status 503, and separately 529, `/query` returns HTTP 503 with `detail == BUSY_ERROR_MESSAGE` (different from `CONFIG_ERROR_MESSAGE`), same body rule.
   Also: an error carrying a non-classified status (e.g. 500, 401) or a non-integer status value still returns the generic 500.
3. The above holds for exception objects shaped like each of the four providers' (status in `.status_code` for mistral/openai/anthropic, in `.code` for google-genai), constructed without network. Where a provider SDK is importable, its real exception class is used; otherwise a stand-in with the same attribute is used and the test says so.
4. A generic exception (e.g. `RuntimeError`) still returns 500 with `GENERIC_ERROR_MESSAGE`; `LLMConfigError` still returns 503 with `CONFIG_ERROR_MESSAGE`.
5. The raw exception is still logged (check with `caplog`).
6. A successful answer and a gate-level or refusal `grounded:false` response are byte-for-byte unchanged.
7. A mocked provider function is called exactly once per `/query` on a 429 and on a 503 (no retry).
8. `git diff` shows no change under `frontend/`, `backend/config.py`, `backend/.env.example`, or deploy configs.
9. CI command `pytest tests/test_embedder.py tests/test_web_loader.py -v` still exits 0; new tests run without an API key.

## Edge Cases
- 429 from the rewrite call (opt-in feature): already swallowed; the answer call may then also 429 and is handled by this spec.
- 503 from the answer call after retrieval succeeded: the user's question is lost from the input box (existing frontend behavior); out of scope.
- Gemini returns 429 for quota and 503 for overload with different SDK classes (`ClientError` vs `ServerError`, status in `.code`); Mistral uses one `SDKError` with `.status_code`. Classification must read the status, not the class name alone.
- Provider 5xx other than 503 (500, 502, 504): not classified unless the owner includes them. ASSUMPTION: they stay generic 500.
- Anthropic 529 "overloaded": treated like 503 (now in Requirement 1). Whether the pinned anthropic SDK exposes 529 via `status_code` is to be confirmed in planning.
- Any unrelated exception that happens to carry an integer `code` of 429/503 would be misclassified; accepted as very low risk.
