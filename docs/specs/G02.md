# G02

## Status
APPROVED (2026-09-26; human approval given in PLAN-G02 session, A1 tolerant policy and A3 additive field accepted)

## Problem
`POST /upload` reports every file it saved to disk as if it had been indexed. A file that yields no text (unreadable or corrupt, scanned PDF with no OCR, DOCX holding only tables, whitespace-only content) is dropped silently by the loader but is still listed in `filenames`. The UI then shows it as "indexed", so the user believes a document is searchable when none of its content is. Questions about it fail with "not found in your documents" and nothing tells the user why.

## Current Behavior
- FACT (code, `backend/api/main.py:/upload`): `saved_filenames.append(file.filename)` runs right after each file is written to staging. The response returns `"filenames": saved_filenames` regardless of what ingestion produced.
- FACT (code, `loader.py`): `_load_text`, `_load_docx` and `_load_pdf` each catch every exception, log a warning, and return `[]`. An empty file body also returns `[]`. The caller cannot tell "failed to read" from "read but empty". `_ocr_page` also swallows failures.
- FACT (code, `pipeline.py:ingest`): returns one integer (total chunks). It carries no per-file information.
- FACT (code): the loader labels each document with the on-disk name. `filepath.name` is the disambiguated name (`notes (1).pdf`) and PDFs use `name#pageN`. The response uses the original `file.filename`, so the two do not match when a batch holds duplicate names.
- FACT (code, `main.py`): the only failure signal is `chunk_count == 0` → HTTP 400 "No readable text was found in the uploaded file(s)." If at least one file yields text, the request returns 200 and the unreadable ones are not mentioned.
- FACT (code, `frontend/app/app/page.tsx`): the banner renders `filenames` joined by ", " followed by "N passages indexed". In append mode `filenames` accumulate across uploads. There is no place to show a skipped file.
- FACT (code, `frontend/lib/types.ts`): `UploadResponse` has `session_id`, `filenames`, `chunks`, `status` only.
- INFERRED (not run): python-docx `doc.paragraphs` excludes table cells, headers and footers, so a table-only DOCX would be skipped and still listed (see G21).
- The defect was not reproduced by running; see Reproduction.

## Expected Behavior
- REQUIREMENT (REQ-I02; 06 §G02): the `filenames` returned by `/upload`, and shown as "indexed", are exactly the uploaded files that contributed at least one chunk. A file that contributed none is not reported as indexed. The user is told which files were skipped and why, in wording they can act on.
- DECISION (policy is unchanged; D-U11 not resolved here): a mixed batch (some files readable, some not) stays **tolerant**, as today. This spec changes what is reported, not whether such a batch succeeds. Any move to atomic failure is D-U11's decision.

## Reproduction
Keyless; needs only the backend running, with a stub or local embedder. `validate_file` rejects empty files (`File is empty.`) so the fixtures must be non-empty.
1. Create a new session: `POST /upload` with `good.txt` (some prose) and `blank.txt` (only spaces/newlines, e.g. 10 bytes).
2. Expected: `filenames == ["good.txt"]`, and `blank.txt` reported as skipped.
3. Observed (by code reading): 200 with `filenames == ["good.txt", "blank.txt"]`, `chunks` = chunks of `good.txt` alone.
4. Variant: replace `blank.txt` with `broken.pdf` containing non-PDF bytes. Same result, and the failure appears only in server logs.
5. Variant: two uploads named `a.txt`, one readable and one whitespace-only. The loader's per-file label is `a.txt` and `a (1).txt`, so any fix that maps results back by name must handle this.

## Root Cause
- FACT (code): `filenames` is built from what was staged, not from what ingestion produced. Independently, the loader discards per-file outcome, and `ingest` returns only an aggregate count. The information needed to report truthfully does not currently leave the loader.

## Scope
- The `/upload` response: which filenames it reports as indexed, and a new way to report skipped files with a reason.
- Distinguishing at least two skip reasons for the user: (a) the file could not be read/parsed; (b) the file was read but contained no extractable text.
- Correct attribution of results to the uploaded filename, including duplicate names within one batch.
- Frontend: the type for the extended response and the upload banner, so skipped files are visible and are not counted as indexed.
- Tests for the above.

## Out of Scope
- D-U11 policy: atomic failure of a mixed batch, and dedup of re-uploaded files (G27). Tolerant behavior stays.
- G21 (extracting more DOCX/PDF content), G19 (OCR on the Railway image), V-F04. G02 only makes their failures visible. It does not fix the extraction.
- Page-level partial reporting for PDFs (a PDF with some empty pages counts as indexed if any page yielded text).
- `/upload-url`: it ingests one URL, and a zero-text result is already an error (400).
- G13 (raw exception text in 500 details). G02 must not add new raw-exception leakage, but does not fix the existing one.
- Changing status codes or error messages of existing failure paths (400 for no readable text, etc.).
- CORS, allowlists, deploy configs, CI.
- Chunking, embedding, retrieval, grounding.

## Requirements
1. **R1 – Truthful `filenames`.** In a 200 response, `filenames` contains exactly the uploaded files that contributed ≥1 chunk to the index, and none that contributed 0.
2. **R2 – Skipped files are reported.** Every uploaded file that contributed 0 chunks is reported in the response as skipped, identified by its original uploaded filename, with a reason. Every uploaded file appears in exactly one of `filenames` or the skipped list.
3. **R3 – Reason categories.** The skip reason distinguishes "could not be read" (parse/open failure, corrupt file) from "no extractable text" (read fine, nothing to index). Reasons are short, user-safe strings. They never contain exception text, stack traces, server paths or the on-disk staging name.
4. **R4 – Duplicate names.** When one batch contains files with the same name, each is reported independently and correctly. E.g. a readable `a.txt` and an empty-text `a.txt` yield one indexed and one skipped, not both indexed and not both skipped.
5. **R5 – Additive contract.** Existing response fields (`session_id`, `filenames`, `chunks`, `status`) keep their names and types. The skipped-file report is a new, additive field. It is present in every 200 response as a list, empty when nothing was skipped, so clients need no presence check. Its exact name and item shape are fixed in the implementation plan and mirrored in `frontend/lib/types.ts`. Item shape must carry at least the filename and the reason.
6. **R6 – `chunks` unchanged.** `chunks` still equals the number of chunks from this request's own files (G01 R3). Skipped files contribute 0.
7. **R7 – Failure paths unchanged.** If no file contributes text, the response is still HTTP 400 with the existing "No readable text was found in the uploaded file(s)." message, and the `_cleanup_if_new` behavior is unchanged. Validation failures (400), too many files, invalid session id, and ingestion exceptions (500) are unchanged.
8. **R8 – UI shows truth.** After an upload with skipped files, the UI (a) lists only indexed files in the "indexed" banner and counts, and (b) shows the user, near that banner, that specific files were skipped and why. It does so on the append path as well as the new-session path. The UI must not treat a partly skipped upload as an error state that blocks asking questions. Skipped files must not be added to the accumulated indexed-file list.
9. **R9 – Tolerant policy preserved.** A batch with at least one readable file and at least one skipped file still returns 200 and indexes the readable files. Which of these is required to change if D-U11 later decides otherwise is not decided here.
10. **R10 – G01 preserved.** Per-request staging, isolation and exactly-once guarantees hold (all G01 acceptance criteria still pass).
11. **R11 – `/upload-url` unaffected.** Its request/response and behavior are unchanged. (If the shared type gains the new field, the URL response either supplies an empty list or the field is optional in the type; the plan decides.)

## Acceptance Criteria
1. AC1 (R1, R2, R6): upload `good.txt` (prose) + `blank.txt` (whitespace only, non-empty bytes) to a new session. Response is 200; `filenames == ["good.txt"]`; skipped list has exactly one item for `blank.txt`; `chunks` equals the chunks of `good.txt` alone; the session's stored chunk count equals `chunks`.
2. AC2 (R3): upload `good.txt` + `blank.txt` (whitespace only) + `broken.pdf` (bytes that are not a PDF). `broken.pdf` is skipped with the "could not be read" category and `blank.txt` with the "no extractable text" category. The two reason values differ in a way a test can assert. Neither reason string contains `Traceback`, `/tmp`, the staging directory name, or an exception class name.
3. AC3 (R4): one batch with two files both named `a.txt`, one with prose and one whitespace-only. Result: `filenames == ["a.txt"]` and one skipped item named `a.txt`; total chunks equal the prose file's chunks. The reverse upload order gives the same outcome.
4. AC4 (R2): for a mixed batch, the list of `filenames` plus the skipped filenames is a permutation of the uploaded filenames (same multiset), with no file in both.
5. AC5 (R5, R6): a fully readable batch (sequential, new session and append) returns 200 with the same `session_id`/`filenames`/`chunks`/`status` values as before, plus an empty skipped list.
6. AC6 (R7): a batch where every file is unreadable/empty-text returns 400 with the unchanged message; if the session was new, it is cleaned up as before. An existing session is not deleted (existing `is_new_session` guard).
7. AC7 (R7): too many files, invalid session id, unsupported extension and empty-file (0 bytes) requests return the same status and message as before.
8. AC8 (R9, R10): the G01 concurrency tests (`backend/tests/test_upload_concurrency.py`) still pass unmodified, except one assertion in `test_sequential_new_and_append_response_contract` whose exact response key set gains `skipped` (human-approved in PLAN-G02; this constrains the mechanism; see Regression Requirements on `load_documents`), and a concurrent variant where one request carries a whitespace-only file still gives every request the correct `filenames`, skipped list and `chunks`.
9. AC9 (R11): `/upload-url` responses are unchanged for its existing success and error cases (it has no keyless test today; assert via the endpoint function with a stubbed loader, or by code inspection if a stub is not practical, and record which).
10. AC10 (R5, R8): `frontend/lib/types.ts` `UploadResponse` describes the new field and `npm run lint` and `npm run build` (from `frontend/`) pass with no new errors. (Requires `npm install`; see Verification Strategy.)
11. AC11 (R8): manual UI check against a local backend (see Verification Strategy): after uploading a good + blank file, the banner lists only the good file and the blank file's name and reason are visible; after a second (append) upload with another skipped file, both skipped files are shown, the indexed list contains only readable files, and the question box remains usable.
12. AC12: the CI command (`pytest tests/test_embedder.py tests/test_web_loader.py -v`, from `backend/`) still exits 0. New backend tests need no API key and no model download beyond what G01's test already uses (stubbed embedder).

## Edge Cases
- Whitespace-only text file (non-zero bytes): skipped, "no extractable text". (A 0-byte file is rejected earlier by `validate_file`; unchanged.)
- PDF with pages of no text layer and OCR off/unavailable (G19/V-F04): skipped as "no extractable text"; the reason may mention scanned/image-only content but must not assert OCR is available.
- PDF where some pages have text and some do not: indexed, not reported as skipped (page-level detail out of scope).
- Corrupt PDF/DOCX: "could not be read".
- DOCX with only tables/headers (G21): skipped as "no extractable text" until G21 changes extraction.
- Duplicate names in one batch (R4), including where the disambiguated on-disk name (`a (1).txt`) already equals another uploaded file's real name (e.g. uploading `a.txt`, `a.txt`, and a file literally named `a (1).txt`). Attribution must still be correct or, at minimum, must not mislabel files. Plan must state how it avoids ambiguity.
- Non-ASCII or very long filenames: reported verbatim as uploaded; UI truncation stays as `shortName`.
- Skipped list in append mode: reflects only the latest request. The UI decides how long to show it, and it is never merged into indexed files.
- Ingestion exception after some files loaded: existing 500 path; no skipped report required.
- Unsupported file types cannot reach the loader (rejected by `validate_file` with 400). The loader's own "skip unsupported" branch is not a G02 case.
- Same-request all-skipped in an existing session: 400 as today; the existing session survives.

## Assumptions
- A1 (high): tolerant policy for mixed batches is the intended current behavior and is safe to preserve pending D-U11. Evidence: OCR docstring says a bad page "shouldn't fail the whole upload"; not confirmed by the owner.
- A2 (medium; needs-verification: yes, U1): a file that reaches the loader with text always yields ≥1 chunk, so "contributed 0 chunks" equals "loader returned no docs for it". The plan must confirm against `chunk_documents`; if wrong, "contributed 0 chunks" is still the governing rule.
- A3 (medium; needs-verification: no, owner): the only API consumer is this repo's frontend, or clients ignore unknown JSON fields, so an additive field is backward compatible.
- A4 (high): G01's per-request staging is merged (`d782338`), so "this request's files" is well defined.
- A5 (medium): showing skip reasons inline in the existing banner area is acceptable UX. The owner may want different wording or placement (U3).
