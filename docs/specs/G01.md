# G01

## Status
APPROVED (human approved as written, 2026-09-26; same-name uploads = distinct uploads; no CI wiring)

## Problem
When two or more `/upload` requests target the same `session_id` at overlapping times, each request ingests files staged by the others. Chunks are duplicated in the index and the reported `chunks` count is wrong. One request can also delete another's staged files.

## Current Behavior
- FACT (code, `backend/api/main.py:/upload`): every request stages files into `/tmp/rag_sessions/<session_id>/`, a directory keyed by session only. It then calls `pipeline.ingest(tmp_dir, session_id)`, which calls `load_documents(directory)`. That function ingests every supported file under the directory (`rglob("*")`, `loader.py`). The request then `rmtree`s the whole directory.
- FACT (code): the same `rmtree` also runs on the `HTTPException` path (e.g. a later file in a request fails validation) and on the generic-exception path.
- FACT (code, `chroma_store.py:add`): `_add_lock` serializes id allocation only (`count()` then ids). It does not control which files a request ingests.
- FACT (OBSERVED, `03-runtime-and-behavior.md` §5): four parallel `/upload` calls to one session with four different 1-chunk files all returned 200 with `chunks` = 3, 2, 4, 4. The collection held 15 chunks where 6 were expected (2 pre-existing + 4). Ids were unique (15/15).
- FACT (code): `disambiguate_filename` only de-duplicates names within a single request's batch. Two requests staging the same filename overwrite each other's file on disk.
- INFERRED (not observed): request B's `rmtree` (success or failure path) can delete request A's staged files before or during A's ingest. A could then ingest fewer files than it uploaded, or fail with a 500.

## Expected Behavior
- REQUIREMENT (REQ-I01, REQ-I02, REQ-E18): a `/upload` request indexes exactly the files it uploaded, each exactly once, regardless of other requests running against the same session. The `chunks` value it returns equals the number of chunks produced from its own files. A request's success or failure never affects another request's files.

## Reproduction
1. Start the backend (single uvicorn process).
2. Create a session: `POST /upload` with one small text file. Note `session_id`.
3. Concurrently send 4 `POST /upload` requests with that `session_id`, each with a different one-chunk `.txt` file.
4. Expected: each response `chunks == 1`. Collection count = pre-existing + 4.
5. Observed (03 §5): responses 3, 2, 4, 4; collection 15 vs 6.
The result is timing-dependent. Requests must overlap between staging and `rmtree`; use a client that fires them simultaneously.

## Root Cause
- FACT (CONFIRMED by the observed numbers and code): the staging directory is per session, not per request, and `ingest` processes the whole directory. The store lock covers id allocation, not the set of files ingested.

## Scope
- The `/upload` endpoint's behavior for overlapping requests to the same `session_id`, covering:
  - which files a request ingests;
  - the `chunks` count and `filenames` it reports;
  - isolation of staged files between requests, including cleanup on success and on failure.
- A regression test for the above.

## Out of Scope
- G02: reporting files that yielded no text, and any change to the response shape or the atomic/tolerant policy (D-U11).
- G27: de-duplicating the same file re-uploaded in a later request. See Requirement 5.
- Multi-worker / multi-process safety (REQ-B09; the app is single-process by design).
- `/upload-url`. It has no staging directory. It shares `ChromaStore.add`, which is already lock-protected for id allocation.
- Frontend changes. The UI already prevents concurrent uploads via its `uploading` flag.
- Changing `ChromaStore` id scheme, TTL, or session cleanup.
- Broader test-suite work (G08). Only the G01 regression test is in scope.

## Requirements
1. **R1 – Own files only.** A `/upload` request ingests only the files it uploaded in that request. Files staged by other overlapping requests, including other requests to the same `session_id`, are never ingested by it.
2. **R2 – Exactly once.** Under any number of overlapping same-session requests, each uploaded file's content is indexed exactly once. The session's total chunk count equals the sum of the chunks each file yields when uploaded alone.
3. **R3 – Accurate count.** The `chunks` field in each response equals the number of chunks produced from that request's own files.
4. **R4 – Cleanup isolation.** A request's cleanup, on success, validation failure, or ingestion failure, removes only that request's own staged data. It never removes or alters another in-flight request's staged files.
5. **R5 – Same filename across requests.** Two overlapping requests that upload files with the same name each get their own file indexed, because each upload is a distinct upload. Neither overwrites the other's staged copy. Whether identical content should be de-duplicated is G27's decision.
6. **R6 – No stale carry-over.** Files left on disk by a previous request (e.g. a process killed mid-request) are not ingested by a later request.
7. **R7 – No contract change.** The success response shape (`session_id`, `filenames`, `chunks`, `status`), status codes and error messages are unchanged for non-concurrent use.
8. **R8 – Single-process only.** The fix must be correct for the supported single uvicorn process. It need not be correct across multiple processes.

## Acceptance Criteria
1. AC1 (R1, R2, R3): a test issues N ≥ 4 simultaneous `/upload` calls to one existing session, each with a distinct one-chunk file. Every response returns HTTP 200 with `chunks == 1`. The session's final chunk count equals pre-existing + N. Each source filename appears exactly once, with one chunk.
2. AC2 (R1, R3): same as AC1 with files of differing chunk counts (e.g. 1, 2, 3). Each response's `chunks` equals that file's own count, and the total equals the sum.
3. AC3 (R4): one request fails validation (e.g. unsupported extension or oversize) while other same-session requests are in flight. The failing request returns 400, and the others still return 200 with correct counts and complete indexing.
4. AC4 (R5): two overlapping requests upload different-content files with the same name to one session. Both contents are indexed, and neither response's count includes the other's chunks.
5. AC5 (R6): before a request, a stray supported file (e.g. `stray.txt` with distinct content) is placed in `/tmp/rag_sessions/<session_id>/` for the target session. After the request, the session contains no chunks from `stray.txt`, and the response `chunks` equals the count for the uploaded file(s) only. (This checks the current staging root, and holds for any mechanism that keeps staging under `/tmp/rag_sessions/`.)
6. AC6 (R7): a single sequential upload (new session, and append to an existing session) returns the same response shape, status and `filenames` as before. Existing error paths (too many files, invalid session id, unsupported type, no readable text → 400) behave as before.
7. AC7 (R4): after all requests complete (success or failure), no per-request staging data remains on disk.
8. AC8: the CI command (`pytest tests/test_embedder.py tests/test_web_loader.py -v`) still exits 0. The new test does not require an API key.

## Edge Cases
- Only one of several overlapping requests contains readable text: the others must still succeed. Whether a zero-chunk request creates or removes a session is unchanged from today (`_cleanup_if_new`).
- Overlapping requests where `session_id` is omitted: each gets its own new UUID, so there is no sharing.
- A request with an existing session that yields 0 chunks must not delete that session (today's `_cleanup_if_new` guards this via `is_new_session`; keep it).
- Client disconnects or the server is killed mid-request: staged data may remain (see R6, which requires it not to leak into other requests' ingestion).
- Very large batches (`max_files_per_upload`): behavior unchanged apart from isolation.
- Two requests racing on the same filename: see R5.
- A request that hits an exception during ingestion while another request is still writing: R4.

## Regression Requirements

- `_add_lock` id-range behavior in `ChromaStore.add` remains correct (ids unique).
- Within-batch same-name disambiguation (`disambiguate_filename`) keeps working.
- `/upload-url` behavior is unchanged.
- The grounding contract is not touched.
- No new heavy dependencies (low-memory hosting constraint).
- No changes to CORS, URL allowlists, deploy configs or CI files.

## Constraints
- Single uvicorn process (REQ-B09); the in-process approach is acceptable.
- Config values come from `config.py` only; no ad hoc `os.getenv` (CLAUDE.md).
- No paid LLM/embedding calls in the test. It must use a stub or the local embedder and avoid `test_pipeline.py`. Assumption A3 below covers whether the local embedder is available.
- The spec deliberately does not prescribe the mechanism. Per-request staging vs. a per-session lock is a planning-phase choice, and it must satisfy R1–R8. The backlog notes that per-request staging is the direct fix for the stated root cause. A lock alone would satisfy R1/R2/R3 but still leaves R5/R6 to be addressed.
- Existing tests in CI are limited to `test_embedder.py` and `test_web_loader.py`. If the new test is to run in CI, editing `.github/workflows/` needs explicit user instruction (see Unknowns U2).
