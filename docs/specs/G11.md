# G11

## Status
APPROVED (2026-09-27, owner approval in this session)

## Problem
`DELETE /sessions/{session_id}` accepts any path string as `session_id` and passes it straight into a ChromaDB collection name (`f"session_{session_id}"`) with no format check. Every other route that accepts a client-supplied `session_id` (`/upload` with an existing session, `/upload-url`, `/query`) validates it first with `_validate_client_session_id`, which requires it to parse as a UUID. `DELETE` is the one route that skips this check.

## Current Behavior
- FACT (code, `backend/api/main.py:300-303`):
  ```python
  @app.delete("/sessions/{session_id}")
  async def delete_session(session_id: str):
      deleted = pipeline.chroma_store.delete_session(session_id)
      return {"deleted": session_id, "success": deleted}
  ```
  No call to `_validate_client_session_id` or any other check on `session_id` before it reaches the store.
- FACT (code, `backend/api/main.py:81-88`): `_validate_client_session_id` does `uuid.UUID(session_id)` and raises `HTTPException(400, "Invalid session_id.")` on `ValueError`. It is called from `/upload` (line 141, only when a client passes an existing `session_id`), `/upload-url` (line 238), and `/query` (line 287).
- FACT (code, `backend/src/storage/chroma_store.py:112-117`):
  ```python
  def delete_session(self, session_id: str) -> bool:
      try:
          self.client.delete_collection(f"session_{session_id}")
          return True
      except chromadb.errors.NotFoundError:
          return False
  ```
  Only `NotFoundError` is caught. Any other exception the chromadb client raises for a malformed collection name (e.g. one built from a `session_id` containing `/`, null bytes, or other characters chromadb's own collection-name rules reject) propagates unhandled out of the route, becoming FastAPI's default 500 handler — which returns the exception text in the response detail (separately tracked as G13; not fixed here).
- FACT (code, `frontend/lib/api.ts:126-132`):
  ```ts
  export async function deleteSession(sessionId: string): Promise<void> {
    try {
      await fetch(`${getApiBase()}/sessions/${sessionId}`, { method: "DELETE" });
    } catch {
      // best-effort — don't block the UI reset on a network failure
    }
  }
  ```
  Called from `frontend/app/app/page.tsx:148` with the session's own server-issued UUID. The function never inspects `res.ok`, the status code, or the response body — it only catches a thrown (network-level) error. This corrects `docs/PROJECT_BACKLOG.md` G11's note that the frontend was "unverified beyond 04" on this point: the frontend does call `DELETE /sessions/{id}`, but is provably indifferent to its response, including any status code.
- INFERRED, not run (chromadb is not installed in this session's environment; see CLAUDE.md "Not verified"): whether `self.client.delete_collection(f"session_{session_id}")` with a garbage `session_id` (long string, path-like segments, control characters) raises `NotFoundError`, some other chromadb exception, or nothing. Behavior for `session_id` values chromadb's own name validation would reject is UNKNOWN pending the implementation phase's test run.
- Not reproduced by running the server (no backend deps in `venv/`, per CLAUDE.md); this is a code-read finding.

## Expected Behavior
- REQUIREMENT (spirit of REQ-E08; consistency with the sibling routes): a client-supplied `session_id` on `DELETE /sessions/{session_id}` is validated as a UUID before use, exactly as it already is on `/upload`, `/upload-url`, and `/query`. An invalid format is rejected with `400` before any store call, never reaching chromadb.
- DECISION (this spec, not a new backlog decision): reuse the existing `_validate_client_session_id` helper and its existing `400 "Invalid session_id."` contract, rather than introduce a second validation style. This is the smallest change consistent with the other three routes and doesn't require picking between "400" and "200 success:false" for the invalid-format case — the codebase already answered that question for every other route.
- Deleting a well-formed but non-existent (or already-deleted) UUID session continues to return `200 {"deleted": ..., "success": false}`, unchanged — this is not the bug. Only the missing-validation gap is in scope.

## Reproduction
Keyless; needs only the backend running (any embedder config — this path never reaches ingestion or the embedder).
1. Create a session via `POST /upload` (any readable file) to get a real `session_id`.
2. `DELETE /sessions/not-a-uuid` → expected `400 {"detail": "Invalid session_id."}` (matching `/query`'s behavior for the same malformed input). Observed today (by code reading): `200 {"deleted": "not-a-uuid", "success": false}` (chromadb raises `NotFoundError` for a collection name that was never created, so it's caught) — the request "succeeds" as a no-op rather than being rejected as malformed.
3. `DELETE /sessions/` + a value chromadb's collection-naming rules reject outright (e.g. containing `/`, or exceeding chromadb's name-length limit) — behavior is UNKNOWN (Unknowns U1); this is the case that may currently 500 with raw exception text instead of returning `200 success:false`.
4. `DELETE /sessions/<the real session_id from step 1>` → `200 {"deleted": ..., "success": true}`; unchanged, not part of this spec.

## Root Cause
FACT (code): `_validate_client_session_id` was added and wired into `/upload`, `/upload-url`, and `/query`, but the `DELETE /sessions/{session_id}` route was never updated to call it — an omission, not a deliberate design choice (nothing in the route or its docstring, there is none, suggests intent to skip validation here specifically).

## Scope
- Add UUID-format validation to `DELETE /sessions/{session_id}`, using the existing `_validate_client_session_id` helper, before any call to `pipeline.chroma_store.delete_session`.
- Tests pinning: invalid format → 400; well-formed nonexistent UUID → 200 success:false; well-formed existing UUID → 200 success:true (regression).

## Out of Scope
- **`/feedback` validation** (the other half of G11's title). Blocked by **D-U05** (purpose/consumer of `/feedback`; open in `docs/PROJECT_BACKLOG.md`, unresolved in `docs/DECISIONS.md`). Validating a shape that may be removed or redesigned by G12 is wasted work per the backlog's own dependency note. This spec makes no change to `/feedback` or `FeedbackRequest`.
- G13 (raw exception text in 500 responses). If Unknowns U1 confirms that some malformed `session_id` values currently reach chromadb and raise a non-`NotFoundError` exception, this spec's fix removes that path (they're now caught by the UUID check first) but does not otherwise touch error-detail formatting elsewhere in the file.
- Whether to move `delete_session`'s synchronous chromadb call off the event loop (a scope question the backlog explicitly leaves open; no evidence this causes an observed problem, and it's unrelated to input validation).
- Rate limiting behavior on `DELETE` (already covered by the existing global `InMemoryRateLimiter` middleware; unchanged).
- Any change to what `200 success:false` vs `404` means for a not-found session — that contract is unchanged, only the invalid-format case moves from `200 success:false` to `400`.
- `/upload`, `/upload-url`, `/query` — already validated; no changes.

## Requirements
1. **R1 – Validate before use.** `DELETE /sessions/{session_id}` calls `_validate_client_session_id(session_id)` before calling `pipeline.chroma_store.delete_session`. A `session_id` that is not a valid UUID (per `uuid.UUID(...)` parsing, matching the existing helper's exact rule) results in `HTTPException(400, "Invalid session_id.")`, with the same detail string the other three routes already use, and `delete_session` on the store is never called.
2. **R2 – No change to existing success/not-found contract.** A well-formed UUID that does not correspond to any existing collection still returns `200 {"deleted": <session_id>, "success": false}`. A well-formed UUID for an existing session still returns `200 {"deleted": <session_id>, "success": true}` and actually deletes it. Response field names and shape are unchanged.
3. **R3 – No new heavy dependency, no config change, no route signature change** beyond adding the validation call. `session_id` stays a plain path parameter.
4. **R4 – `/feedback` untouched.** No field validation, length caps, or behavior change to `POST /feedback` or `FeedbackRequest` in this change.

## Acceptance Criteria
1. AC1 (R1): `DELETE /sessions/not-a-uuid` returns `400` with `{"detail": "Invalid session_id."}`. The store's `delete_session` is not invoked (assert via a spy/mock in the test, following the pattern available in `test_upload_concurrency.py`).
2. AC2 (R1): a sample of other invalid formats — empty string is not reachable as a distinct path segment (FastAPI path matching), so use `123`, a string with a slash-like segment such as `abc%2Fdef` (URL-decoded before it reaches the route — verify what the route actually sees), and a 200+ character garbage string — all return `400`, none reach the store, none return `500`.
3. AC3 (R2): a well-formed random UUID (e.g. `uuid.uuid4()`) that was never used as a session returns `200 {"deleted": "<uuid>", "success": false}`.
4. AC4 (R2): create a session via the ingestion path used in existing tests (e.g. seeding a collection the way `test_upload_concurrency.py`'s `_seed_session` does), then `DELETE` it with its real UUID: returns `200 {"deleted": "<uuid>", "success": true}`, and the collection no longer exists afterward (assert via the store, e.g. `exists()` or a second delete returning `success: false`).
5. AC5 (R1, R3): the fix is confined to `backend/api/main.py`'s `delete_session` route function — no changes to `chroma_store.py`, `config.py`, or the route's path/HTTP method.
6. AC6: the CI command (`pytest tests/test_embedder.py tests/test_web_loader.py -v`, from `backend/`) still exits 0; the new test file is not added to that CI command (no explicit instruction to modify CI, per CLAUDE.md).
7. AC7 (R4): `POST /feedback` and `FeedbackRequest` are byte-for-byte unchanged in `backend/api/main.py` (diff review).

## Edge Cases
- Well-formed UUID, wrong case or with/without hyphens in a form `uuid.UUID()` still accepts (e.g. `uuid.UUID` also accepts a 32-hex-digit string without hyphens) — this passes validation today via the shared helper and must keep doing so; not a new behavior, just confirms the reused helper's existing tolerance carries over.
- A `session_id` that collides with another route's path shape is not applicable — path is fixed as `/sessions/{session_id}` with no sibling routes under `/sessions/`.
- Deleting the same valid session twice in a row: first call `success: true`, second call `success: false` (already-gone) — unchanged, not part of this fix, but should not regress (covered incidentally by AC4 if extended, otherwise left as an existing behavior no test needs to newly assert).

## Unknowns
- U1 (medium): whether a `session_id` value that chromadb's own collection-naming rules reject (as opposed to merely "well-formed UUID string but no such collection") currently raises something other than `NotFoundError` from `delete_session`, producing an unhandled 500. This spec's fix makes it moot for any such value that also isn't a valid UUID (which covers essentially all of chromadb's rejected names, since a UUID string is always chromadb-name-safe), so U1 does not block writing or verifying AC1–AC7, but the implementation phase's test run should confirm no such value can now reach the store un-validated.
- U2: exact FastAPI path-parameter decoding for a `session_id` containing an encoded slash (AC2) — left to the implementation phase's actual test run to observe rather than asserted here from code reading alone.

## Assumptions
- A1 (high): `_validate_client_session_id`'s existing UUID-parse rule and `400 "Invalid session_id."` message are the correct contract to extend to this route, since three other routes already use exactly this rule and message — introducing a different one for the fourth would be the inconsistency, not the fix. Confirmed by the pattern already established in the code, not by the owner directly.
- A2 (medium): the frontend's total indifference to this route's response status (Current Behavior, `deleteSession`) means changing the invalid-format case from `200` to `400` carries no frontend regression risk. If a future or external client does check status codes, `400` for a malformed id is the more correct contract, matching the other three routes.
