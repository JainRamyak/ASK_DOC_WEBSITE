# G27

## Status
APPROVED (2026-09-27, owner, via /implementation-plan G27 invocation confirmed as approval — session PLAN-G27-2026-09-27). Option B (skip identical content, per-session SHA-256 identity) — see DECISION REQUIRED below and `docs/DECISIONS.md`.

## Problem
Uploading the same document again to an existing session (a later `/upload` request with the same `session_id`) appears to index it a second time. The session then holds two identical copies of every chunk. The user sees the file listed twice, "N passages indexed" grows, and retrieval can fill its top-k slots with the same passage twice. Nothing tells the user the file was already there.

## Current Behavior
- FACT (code, `backend/src/storage/chroma_store.py:add`): chunk ids are `f"{session_id}_{existing + i}"`, where `existing` is the collection's current count. Ids are positional and carry no file or content identity, so a re-upload can never collide with an earlier copy. `collection.add` always appends.
- FACT (code, `backend/src/pipeline.py:_store_docs`): chunks are embedded and stored unconditionally. No lookup of already-indexed sources or content exists anywhere in the ingest path.
- FACT (code, `chunker.py`): chunk metadata is `text`, `source` (on-disk name, or `name#pageN` for PDFs), `page`, `chunk_index`. There is no content hash and no stable document id.
- FACT (code, `main.py:/upload`): `filenames` lists every file that yielded text in this request. The response has no notion of "already indexed". `/upload-url` has the same shape and the same gap (same URL twice appends twice).
- FACT (code, `frontend/app/app/page.tsx:55,76`): in append mode the UI does `[...prev, ...res.filenames]`, so the same name is shown twice in the banner. The chunk count is taken from the response, not deduplicated.
- INFERRED (not run): retrieval requests `top_k * 4` candidates and reranks. Two identical chunks get identical scores, so both can survive into the final `top_n` context and the `sources` list, which reduces the diversity of context sent to the LLM. Grounding correctness is not affected (the text is the user's own), but answer quality and citation clarity are.
- Interaction with G01: a same-named file in two *overlapping* requests is treated as two distinct uploads (G01 R5, A2). G27 owns whether identical content should be collapsed.
- Not observed: this has not been run. `venv/` lacks pytest/uvicorn/chromadb (CLAUDE.md "Not verified", re-confirmed this session: `import pytest, chromadb, fastapi` fails). Confidence LOW-MEDIUM, code-read only.

## Expected Behavior
- REQUIREMENT (REQ-U11 dedup half; resolved via DECISION REQUIRED, Option B): identity is the SHA-256 hash of the uploaded file's raw bytes (for `/upload-url`, of the fetched page text), scoped to one session. When `/upload` receives a file whose hash already has ≥1 chunk stored in that session, the file is **not** re-ingested; it is reported as already indexed, distinctly from both `filenames` (newly indexed) and G02's `skipped` (unreadable/no-text). A file whose bytes differ from anything already in the session — including one with the same name as an existing file — is indexed as new; both versions then coexist under that name.
- REQUIREMENT: the user is never left believing a re-upload did something different from what happened. The response and UI state the outcome plainly (e.g. "already indexed").

## Reproduction
Keyless (stub or local embedder), backend running. Not yet run.
1. `POST /upload` with `notes.txt` (some prose) and no `session_id`. Record `session_id`, `chunks` = N.
2. `POST /upload` with the same bytes as `notes.txt` and that `session_id`.
3. Expected if the append is a defect: `chunks` reports 0 new (or the file is reported as already indexed), and the collection count stays N.
4. Observed (by code reading): 200, `chunks` = N, `filenames == ["notes.txt"]`, collection count 2N, each chunk text present twice with different ids.
5. Variants to run: (a) same content, different filename; (b) same filename, edited content; (c) same URL twice via `/upload-url`; (d) a PDF re-uploaded (per-page `name#pageN` sources).
6. Query check: ask a question whose answer is in `notes.txt` and inspect `sources`; look for the same passage cited twice.
The plan's first step should be a keyless pytest following `tests/test_upload_concurrency.py`'s stub pattern that fails/asserts on current `main` and converts the FACT/INFERRED lines above into observed ones.

## Root Cause
- FACT (code): the store has no document identity. Ids are positional counts and metadata carries no content hash, so nothing in ingest can tell that a chunk already exists. This is a missing capability, not a regression. Whether it is a *defect* depends on D-U11.

## Scope
- Computing a content-hash identity for each uploaded file (`/upload`) and each fetched URL (`/upload-url`), scoped to the session.
- Before ingesting a file/URL, checking whether that hash already has chunks in the session's collection; if so, skipping ingestion of that item.
- Reporting the skip as "already indexed" in the `/upload` and `/upload-url` responses, additive to and distinct from G02's `skipped` field, and not counted in `filenames`.
- Making the check-then-add atomic per session under the existing store lock (R3).
- Showing the "already indexed" outcome in the UI banner, without touching the accumulated indexed-file list beyond adding this outcome's own display.
- Tests for the above, including the concurrent case.

## Out of Scope
- Replacing/updating an existing file by re-uploading an edited version under the same name (Option C) — a same-named file with different bytes is indexed as new, both versions coexist; there is no "update my document" behavior.
- Near-duplicate or fuzzy detection (same text with minor edits, overlapping documents, or same content re-encoded differently, e.g. re-saved PDF with different bytes but same rendered text).
- Cross-session dedup (sessions are isolated by design).
- Retrieval-time dedup of identical chunks (Option D; not needed once ingest-time dedup prevents the duplicates from being stored).
- Atomic-vs-tolerant failure of a mixed batch (the other half of D-U11; G02 already preserved tolerant behavior). Unaffected by this spec.
- G21 extraction fidelity, G19 OCR, chunking/embedding changes, grounding contract, CORS/allowlists, CI, deploy configs.
- Migrating or cleaning duplicates already stored in existing sessions before this change ships (sessions are TTL-bound temp data; A3).
- Per-page identity for PDFs: identity is whole-file-bytes based; a PDF re-uploaded with one changed page is treated as new content, not as a partial duplicate.

## Requirements
1. **R1 – Identity key.** A file's identity is the SHA-256 hex digest of its raw uploaded bytes. A URL's identity (for `/upload-url`) is the SHA-256 hex digest of its fetched, extracted text (the same string `load_url` would chunk), not the raw HTTP response bytes.
2. **R2 – Session-scoped skip.** Before storing a file's/URL's chunks, the pipeline checks whether the session's collection already contains ≥1 chunk with that identity's hash. If yes, the file/URL contributes 0 new chunks and is not re-embedded or re-stored. If no, it is ingested and its chunks carry the hash in their metadata so future uploads can be checked against it.
3. **R3 – Truthful reporting, additive field.** `/upload`'s response gains a new field, `already_indexed` (list of `{"filename": <original name>, "hash": <sha256 hex>}`), always present (empty list when nothing was a repeat). A file that is a repeat appears in `already_indexed` only — never in `filenames` or in G02's `skipped`. Every uploaded file appears in exactly one of `filenames` / `skipped` / `already_indexed` (extends G02 R2's partition).
4. **R4 – `/upload-url` parity.** `/upload-url`'s response gains the same `already_indexed` field (empty list, or one entry keyed by the URL string, when the fetched text's hash is already in the session). Its existing "0 chunks → 400" behavior applies only when the URL is genuinely new and yields no text; a repeat URL is a 200 with `already_indexed` populated and `chunks: 0`, not a 400.
5. **R5 – Session isolation.** Identity and the skip check are per session only (per-collection hash lookup); the same file re-uploaded to a different session is indexed normally there.
6. **R6 – Concurrency-safe.** Two overlapping requests uploading the same file to the same session do not both index it, and do not corrupt the id sequence. The hash-check-then-add sequence for a given session happens under `ChromaStore._add_lock` (the same lock that already serializes id assignment for that process), so the check and the resulting add/skip decision are atomic relative to other adds into that session in this process.
7. **R7 – G01/G02 preserved.** Per-request staging, exactly-once ingestion, and G02's `filenames`/`skipped` contract (and their existing tests) hold unchanged for every case that involves no repeat content. A same-named upload with genuinely different bytes is indexed as new (G01 R5 unaffected).
8. **R8 – Additive contract.** Existing `/upload` and `/upload-url` response fields keep their existing names and types; `already_indexed` is new and additive.
9. **R9 – No heavy dependencies; grounding untouched.** SHA-256 is computed with the standard-library `hashlib`; no new dependency. Retrieval, reranking and the grounding gate are unmodified — dedup happens at ingest time, so there is nothing left to deduplicate at query time.
10. **R10 – UI reflects the truth.** After an upload where some files were repeats, the UI shows which files were already indexed, does not add them a second time to the accumulated indexed-file list, and does not describe the request as an error.

## Acceptance Criteria
1. AC1 (R1, R2, R3): upload `notes.txt` to a new session, then upload the identical bytes (same filename) to that session. First response: `filenames == ["notes.txt"]`, `already_indexed == []`, `chunks == N` (N>0). Second response: `filenames == []`, `already_indexed == [{"filename": "notes.txt", "hash": <sha256 of the bytes>}]`, `chunks == 0`. The session's stored chunk count stays N after the second upload (asserted on the collection, not just the response).
2. AC2 (R1, R2): re-upload the same bytes under a **different filename** (`notes_copy.txt`). Result matches AC1's second-response shape (`already_indexed` entry filenamed `notes_copy.txt`, same hash, `chunks == 0`, collection count unchanged) — identity follows content, not name.
3. AC3 (R7): upload a file with the **same filename** as an already-indexed file but **different bytes**. It is indexed as new: it appears in `filenames`, contributes its own chunks, `already_indexed == []` for it, and the collection count increases by its chunk count. Both versions' chunks are present and retrievable afterward.
4. AC4 (R3): a mixed batch — one new file, one exact repeat of an already-indexed file, one whitespace-only (G02 skip) file — partitions the three filenames across `filenames`, `already_indexed`, and `skipped` respectively with no overlap and no omission (multiset of the three lists equals the uploaded filenames).
5. AC5 (R6): two concurrent requests to the same existing session both upload identical bytes for the same file. After both complete: the collection holds exactly one copy's worth of that content's chunks (never zero, never two) — run repeatedly (as `test_upload_concurrency.py` already does for its own races) to catch a race, since the two requests may interleave either order; both requests return 200; no id collision or exception; staging dirs for both are cleaned up.
6. AC6 (R5): the same bytes uploaded to two **different** sessions are indexed independently in both — `already_indexed` is empty and `filenames` includes the file in each session's own first upload.
7. AC7 (R8, R2): a fully-new, no-repeats batch (sequential, new session and append) returns the same `session_id`/`filenames`/`chunks`/`status` values as before G27, plus an empty `already_indexed` list; the CI-relevant regression suite (`test_upload_concurrency.py`, `test_upload_skipped_files.py`) passes unmodified.
8. AC8 (R4): `/upload-url` with the same URL twice to one session: first call 200 with `chunks > 0`, `already_indexed == []`; second call 200 (not 400) with `chunks == 0`, `already_indexed` naming that URL; collection chunk count unchanged after the second call.
9. AC9 (R9): the retrieval/rerank code path (`retrieve_and_rerank`, `answer_chain`) is untouched by this change (diff-level check in review); a query after a repeat-upload attempt returns the same `sources` it would have without the repeat attempt.
10. AC10 (R10): `frontend/lib/types.ts` describes `already_indexed` on both response types; `npm run lint` and `npm run build` (from `frontend/`) pass with no new errors.
11. AC11 (R10): manual UI check — upload a file, then upload it again (same session); the banner does not list the filename twice in the indexed count, and shows that it was already indexed; a subsequent question is still answerable (the question box is not blocked).
12. AC12: the CI command (`pytest tests/test_embedder.py tests/test_web_loader.py -v`, from `backend/`) still exits 0. New backend tests need no API key and no model download beyond the stubbed embedder already used by G01/G02 tests.

## Edge Cases
- Same bytes, different name (AC2): treated as a repeat — identity is content, not name.
- Same name, different bytes (AC3): treated as new, not a repeat — identity is content, not name. Both versions' chunks remain queryable under the same displayed name.
- Same name and bytes uploaded twice **within one batch** (single request): the within-batch disambiguation (`disambiguate_filename`, from G01) still gives them distinct on-disk names, but they are the same content — the second one is a repeat of the first *within this request*, not just against prior session content. The check must be against "hashes already committed to the session, including earlier files from this same request," not only pre-existing collection state before the request began.
- PDF: identity is whole-file-bytes based, not per-page; a PDF re-uploaded with one changed page is new content (Out of Scope note above).
- File that was previously *skipped* by G02 (no extractable text) and is re-uploaded: not a repeat — nothing was indexed the first time, so there is no existing hash to match; it goes through G02's skip path again, unaffected by this change.
- Session expired and recreated (TTL): the new session's collection is empty, so a "re-upload" there is a first-time upload — not a repeat.
- Re-upload while the first upload of the same file is still mid-ingest in another request to the same session (R6).
- Unicode filenames: identity ignores filename entirely (R1), so this affects only display, which is unchanged from today.
- URL re-fetched with changed content: hashed on the extracted text (R1), so a changed page is indexed as new, not skipped as a repeat — this is intended, not a defect.
- Sessions already containing duplicates from before this change ships (Out of Scope, A3): existing chunks lack the hash-lookup guarantee only in the sense that they were stored before hashes were recorded per chunk (see Constraints on old-schema chunks) — not retroactively deduplicated.

## DECISION REQUIRED — Re-upload of an already-indexed file (2026-09-26, SPEC-G27-2026-09-26)

Question:
When a user uploads a file that is already indexed in the same session (identical content, and/or same name), what should happen: keep both, skip the new copy, or replace the old one, and how is "the same file" decided?

Relevant evidence:
- Code appends unconditionally with positional ids (`chroma_store.py:add`); no identity exists to compare against.
- D-U11 in `docs/PROJECT_BACKLOG.md` bundles this with atomic-vs-tolerant; `05` REQ-U11 covers only the latter and records no dedup intent.
- G01 R5 and G02 deliberately left it undecided. No product statement anywhere says dedup is wanted.

Available options:
1. **A – Keep as is (append).** Change nothing but make it honest: document it, and show the user a note if a name is repeated. Cheapest; duplicate chunks remain and may crowd retrieval.
2. **B – Skip identical content.** Identity = SHA-256 of file bytes (URL: of fetched text), per session. Re-upload of identical bytes is not indexed and is reported as "already indexed". Renamed copies are also caught; edited files with the same name are indexed as new (both versions coexist). Needs a per-chunk `content_hash`/doc id in metadata, and a check-then-add done atomically under the store lock.
3. **C – Replace by filename.** Identity = filename. A re-upload deletes the old file's chunks then indexes the new ones (the "update my document" behavior). Most user-friendly for edits, but needs a delete-by-source API on the store, breaks the positional-id scheme after deletes, is racy under concurrency, and mishandles two genuinely different files with the same name (G01 R5 says these are distinct).
4. **D – Dedup at query time only.** Ingest unchanged; collapse identical chunk texts after retrieval/rerank. No upload contract change, but touches the retrieval path (grounding-sensitive area) and leaves storage and the chunk count inflated.

Impact:
A: no code change, gap closed as "accepted". B: small, additive API/UI change, no deletes needed, concurrency handled with the existing lock; does not help edited re-uploads. C: largest change and highest risk (store API, ids, concurrency), needed only if users expect "re-upload = update". D: quick quality fix but hides rather than resolves duplicates and needs an approved retrieval change per CLAUDE.md.
Suggested (not decided): B is the smallest change that removes the visible duplicate, but choosing it is a product call, so it is not applied here.
